# 请求类型日志

管理员的用量日志新增「请求类型」列，消费成功和失败日志均记录。数据保存在现有 `other.admin_info.request_classification` 中，无需日志表新增列。普通用户日志沿用原有规则隐藏 `admin_info`。

- `type`：NewAPI 关联父窗口后的分类，包含用户请求、相关后台、独立后台、压缩、相关未分类和未知。
- `ingress_type`：最初看到的入站分类。独立后台经过父窗口关联后成为相关后台时，两种分类同时展示。
- `thread_source`、`request_kind`、`subagent_kind`：从协议元数据解析的来源，经过长度与字符限制。
- `root_state`、`related`：根会话解析状态和是否关联父窗口。不记录会话 ID、提示词或工具内容。

分类复用渠道调度使用的元数据解析，包括 HTTP 兼容头和正文嵌套元数据；同时识别 `/responses/compact` 与非空的顶层 `compaction_trigger`。不会从消息正文、回答文本、模型名或错误码猜测请求类型。

分类在渠道选定前采集，父窗口恢复后更新，因此后续 500、503 等失败仍可追溯其请求类型。它是 NewAPI 本地观察，不能代替下游网关的实际诊断；排查 codex2api 时仍需用 NewAPI 请求 ID 对应其日志。

旧日志没有记录该字段时显示「未记录」，不会回填为用户请求。该功能不改变请求内容、分组、账号选择、重试或计费。

调查旧版「独立后台」减少时发现：codex2api 的 API 中转豁免曾把 `relatedToRoot` 清成 false，使已有关联的审核、子代理和标题请求显示为独立后台。2026-09-22 的提交 `1fb2f710` 修复了这条关联保留逻辑。2026-09-21 的旧样本有 5 条子代理、3 条审核、2 条标题请求标为独立后台；2026-09-23 的较新样本中，相同来源已存在成功的相关后台请求。因此标签减少不等于后台调用消失。

`compaction_upstream_unavailable` 表示 codex2api 对携带已知压缩状态的请求没有选到兼容且满足其他调度条件的账号；普通对话携带压缩历史也能触发。`internal_error` 的公开文案可能已经脱敏，仅靠 NewAPI 的概括错误无法确定原始上游原因。
