# 性能失败明细保留策略

模型性能面板的“最终失败记录”存储在主数据库的 `perf_metric_errors` 表中，固定保留最近 **48 小时**。

- 服务启动后异步清理一次，随后每次清理结束等待 5 分钟再执行下一次。
- 超过 48 小时的明细按每批最多 500 条物理删除，避免一次删除全部历史记录。
- 查询接口也强制限制在最近 48 小时内；清理间隔内尚未删除的过期记录不会返回，分页总数同样不包含这些记录。
- 清理任务独立于性能统计开关、刷新间隔和 `perf_metrics_setting.retention_days`，即使关闭统计或将汇总数据设为永久保留，也会继续清理失败明细。
- 只清理失败明细，不删除计费/消费日志、用户日志或模型性能汇总数据。汇总数据仍遵循原来的保留配置。
- 数据库不可用时会记录清理错误，并在下一轮重试；长期故障期间无法保证物理清理按时完成。

页面默认的最近 24 小时是查询时间范围，不是数据库保留期限。查看前一天的失败明细时，需要调整页面时间筛选；超过 48 小时的明细无法恢复，部署前如需留档，应先备份。

删除记录限制的是数据增长，不保证数据库文件立即缩小；磁盘空间回收取决于数据库自身的维护机制。本策略也不负责清理服务器或容器的文本日志。

## 排查 `502 / bad_response_status_code`

NewAPI 的 `service.RelayErrorHandler` 会把上游的 HTTP 状态码带入错误；无法解析为预期结构化错误的响应可能保留 `bad_response_status_code`。关闭错误正文展示时，JSON 解析失败的响应体预览会写入服务日志；响应体读取失败则可能没有这条正文日志。

反向代理在后端重启期间返回 HTML 或空的 502 响应，是这种记录的一种可能来源，但仅凭面板不能确认重启，也不能确定是哪一跳产生了 502。应根据失败时间和请求 ID，核对 NewAPI 的响应体日志、反向代理错误日志、codex2api 日志以及部署/重启时间。
