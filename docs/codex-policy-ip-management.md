# Codex2API IP 封禁管理

入口：**设置 → 运营设置 → Codex2API 审计 → IP 封禁管理**，仅 root 可查看和操作。

## 配置与拦截

- 首次保存审计设置前，沿用 `CODEX2API_POLICY_IP_BLOCK_ENABLED`；保存后使用数据库中的 `Codex2APIPolicySecret.ip_block_enabled`。封禁生成与鉴权使用同一个设置字段。
- IP 开关控制已有封禁的执行，独立于审计采集开关。关闭后记录保留，重新开启时未到期、未解除的记录继续生效。
- 密码及其他登录方式的共同会话创建入口、刷新会话、已登录访问、API Token（包括只读和混合鉴权）统一检查；已建立的 Responses WebSocket 在每次 `response.create` 前检查。
- IP 来源仍使用 Gin 的可信代理配置，IPv4 映射地址及 IPv6 统一规范化。不能用请求头声明管理员身份；已认证的管理员豁免策略 IP 拦截，保留共享出口下的恢复入口。
- 已发送的流不强行中断；后续请求检查新状态。
- IP 查询直接读取共享数据库，不保留可能导致“已解封仍拦截”的本机封禁缓存。保存配置在当前实例立即生效，其他实例仍遵循已有的配置同步周期。

## 查询与解封

管理页默认列出有效记录，每页 50 条，可按精确 IP、用户 ID 和有效／到期／已解除状态查询。显示原因、请求 ID、创建及到期时间、剩余时间、解封人及原因；时间是最近一次查询的快照，点击刷新更新。

“诊断访问限制”分别显示：

1. 被查询 IP 的封禁及当前是否执行。
2. 关联账号状态、当前窗口内违规累计、该账号触发的有效 IP 封禁。
3. 临时登录限流次数及剩余时间。Redis 模式显示共享状态；无 Redis 时只能查询当前实例，其他实例的限流需到对应实例查询。该限流桶也供其他敏感接口使用。
4. 最近 20 条封禁／解封／累计重置事件。原始策略决定始终保留。

“仅解除此 IP”不启用账号，也不清空累计。对同一出口的其他用户同样有效。

“解除关联策略限制”会列出明确的 IP 范围，并恢复能确认由该策略禁用的账号；可单独勾选重置当前违规累计。重置使用决定 ID 边界，不删除审计记录，也不允许旧决定重放再次计数。

历史版本没有记录禁用归属的账号、另行被管理员禁用的账号，不能自动恢复。核实原因后到用户管理单独启用。“启用用户”会提示它不等同于解除 IP 封禁或重置违规累计。

解除操作要求填写原因，并校验决定 ID、策略状态版本及账号认证版本。旧页面与新封禁冲突时返回 409，刷新后重新确认；不能用旧操作误解除新封禁。已解除记录不会因为重启或重开 IP 开关而复活。已删除用户遗留的 IP 封禁仍可单独解除。

解封不会清空临时登录限流，也不会恢复先前已撤销的登录会话。若数据库操作成功但缓存同步失败，管理接口会报告失败；先刷新详情核对已提交的状态，不要假定事务已回滚。

## 管理接口

均位于 root 鉴权的 `/api/option/codex2api-policy` 下，响应禁止缓存：

- `GET /ip-blocks?ip=&user_id=&status=active&page=1`
- `GET /restrictions?ip=&user_id=`，至少提供一项。
- `POST /release`：`user_id`、明确的 `ips[{ip,decision_id}]`、`restore_account`、`reset_strikes`、`reason`；修改账号或累计还需详情中的 `state_revision` 和 `user_auth_version`。

## 性能和验证

封禁开关未启用时不访问封禁表。保存后的配置只在变化时解析；开启时每次鉴权按 IP 主键查找一条有效封禁。成功请求不扫描审计历史、正文或密钥。管理页收起时不查询、展开后按需分页，无新增定时轮询。

本地覆盖配置优先级、HTTP／登录／刷新／持续 WS、可信 IP、管理员恢复、IP 与账号分开解除、违规累计重置、旧决定去重、旧确认拒绝、并发新封禁、删除账号遗留 IP、SQLite 旧表迁移与重启持久性、Redis 限流只读检查和管理端交互。

MySQL／PostgreSQL 使用通用 GORM 迁移、参数化查询及共享行锁助手；当前本机未提供对应测试实例，尚未完成这两个数据库的实际运行验证。以上本机测试不能替代生产多实例与真实数据库负载验收。
